# Managed Stop guard comparison

Predeclared 2026-10-25 after the native module-admission cases. Existing
`plugin.register` refuses competing hooks when its primary or catch returns a
refusal, but admits the competitor when both throw. This alone is not proof
that other native controls cannot enforce a mandatory gate.

Test the existing managed-settings/built-in guard path in **fresh disposable
Linux containers only**. A root-owned `/etc/claude-code/managed-settings.json`
installs a Stop command. Node UID 1000 must not be able to modify that file.
Do not change Windows/owner policy, profiles, credentials or use login services.
Use pinned native 2.1.308, network none, no mounts and a public dummy key.

A user-tier competing module answers `classic.Stop` without delegating. A
separate observer records genuine native start/completion and settled core
trace. A bounded loopback gateway returns one fixed synthetic answer; if native
Stop blocks, it retains and holds the follow-up request. The owner cancels that
held request and exits. No probe edits its own live configuration.

Four immutable configurations:

| Case | Managed command | Question |
| --- | --- | --- |
| `block` | Constant valid Block | Does the built-in guard preserve managed Stop despite the user short-circuit? |
| `missing` | Nonexistent validator executable | Does native managed execution refuse completion on process-launch failure? |
| `fallback` | Fixed shell catches that missing executable and emits Block | Can an existing command wrapper close the missing-validator path? |
| `timeout` | Command starts, then exceeds native one-second timeout | Does the native timeout preserve mandatory blocking? |

Require actual native debug to show managed policy and built-in guard loading,
the competing module's actual tier, actual command result/failure, independently
captured main request(s), and correlated native completion. Distinguish a blocked
follow-up followed by owner abort from an accepted answer. Do not equate an error
notice, process exit or self-reported result with native enforcement.

Gateway ceiling: eight requests, 4 MiB/body; held response deadline 120 seconds.
No external requests are possible. This is a controlled native policy experiment,
not production installation, Codelaya readiness, Windows qualification or proof
that all native enforcement paths have been exhausted.

First cohort retained: managed Block/fallback did block, while missing/timeout
completed as answers, but the gateway's exact prefix check missed managed
feedback containing a literal escaped newline. Positive cases reached the
request ceiling and were cancelled. Use fresh homes for the final matched
cohort; detect the exact reason in native text blocks, without rewriting native
messages, changing any gate, increasing budgets or repairing live settings.

Second cohort retained but invalid: the revised gateway had a duplicate lexical
declaration and never listened. Connection failures do not test native hook
enforcement. Third cohort requires syntax checking and an independent loopback
health response before launching Claude. The health endpoint does not consume
the eight-request budget.

Predeclared extension for the third cohort: repeat the four Stop cases, plus
missing and timeout Stop with `onFailure: "block"`. Compare missing-command
UserPromptSubmit and PreToolUse with and without that setting. For prompt hooks,
blocking must prevent a model request. For tool hooks the gateway first asks the
native Read tool to read the disposable marker: default execution must return
the marker; blocking must return a tool error without that content. The competing
user hook targets the same classic event. No Windows qualification is inferred.
